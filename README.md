# Retail Data Intelligence & Sales Forecasting

An end-to-end analytics and data-engineering project built for the **public Superstore transaction dataset (the standard sample contains 9,994 transaction rows)**. The pipeline uses Python ETL and data-quality checks, a **5-table PostgreSQL star schema (1 fact + 4 dimensions)**, SQL business analytics, **9 time-series features**, a chronological **30-day holdout** for XGBoost vs a same-weekday-last-week baseline, and a safety-checked text-to-SQL prototype.

## Project objective

Turn public retail transaction records into a reproducible analytics workflow: source-data quality checks, curated relational tables, reusable SQL analysis, daily sales forecasting, and interpretable model evaluation.

## Dataset and scope

Download the public Superstore transaction CSV and place it at:

```text
data/raw/superstore.csv
```

The standard sample contains **9,994 transaction rows**. Run the ETL report to verify the row count and any duplicate/invalid records in the exact CSV you use. The ETL validates the expected schema and produces a data-quality report. It does not invent fields that are absent from the source, such as profit, quantity, inventory, unit cost, or store IDs. Since the source contains `Sales`, the forecasting target is **daily sales value**, not unit demand.

Expected fields include:

```text
Row ID, Order ID, Order Date, Ship Date, Ship Mode,
Customer ID, Customer Name, Segment, Country, City, State,
Postal Code, Region, Product ID, Category, Sub-Category,
Product Name, Sales
```

## ETL and data quality

The Python pipeline:
1. Reads and normalizes the source columns.
2. Parses dates and numeric sales values.
3. Standardizes text fields and removes duplicate source rows.
4. Validates required fields, dates and non-negative sales.
5. Builds date, customer, product, location and sales fact outputs.
6. Writes `data/processed/data_quality_report.csv` with source rows, removed duplicates, invalid rows, final fact rows, unique customers/products/locations, and date-dimension size.

## SQL analytics

The SQL layer demonstrates multi-table joins, CTEs, aggregations, views, triggers, indexes, `CASE`-style business logic, and window functions including `LAG()` and `RANK()`. Queries cover monthly sales and growth, product/category performance, customer contribution, geography and shipping mode.

## Forecast evaluation

The target is daily sales value. The model uses **9 time-series features**: day-of-week, month, quarter, trend, lag-1, lag-7, lag-14, and 7-/28-day rolling means calculated from prior observations. On a dataset with sufficient history, the code uses the final **30 days** as a chronological holdout; rows are not randomly shuffled.

The benchmark is a **seasonal-naive forecast** that predicts each test date using sales from the same weekday one week earlier (`lag_7`). XGBoost and the baseline are evaluated on the same holdout dates.

| Model | MAE | RMSE | MAPE |
|---|---:|---:|---:|
| Seasonal naive (same weekday last week) | Generated by `src/forecast.py` | Generated by `src/forecast.py` | Generated by `src/forecast.py` |
| XGBoost | Generated by `src/forecast.py` | Generated by `src/forecast.py` | Generated by `src/forecast.py` |

**Forecast scores are not hard-coded:** the actual MAE, RMSE, MAPE, train/holdout counts, feature count and percentage improvement are written to `data/processed/forecast_metrics.csv` after the source CSV is supplied and the model is run. MAPE is computed only on holdout rows with non-zero actual sales. Predictions and absolute errors are saved to `data/processed/sales_forecast.csv`.

## Text-to-SQL prototype

The `genai/text_to_sql.py` module is an offline, template-based demonstration rather than a live LLM integration. It accepts a small set of example questions and validates generated SQL as read-only `SELECT`/`WITH` queries before use. The safety checks reject mutating statements and multiple SQL statements.

## Tests and continuous integration

The test file defines **9 pytest cases** (including parameterized unsafe-SQL cases) covering ETL transformations, duplicate handling, forecast metric calculations, and text-to-SQL safety. GitHub Actions installs dependencies and runs the test suite on pushes and pull requests to `main`. The test count describes the authored suite; confirm the actual pass count by running `pytest -q`.
